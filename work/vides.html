Case study Arya Omnitalk · production

VIDS — edge AI that logs every vehicle on the highway, not just the violators.

VIDS (Video Incident Detection System, VIDES inside the company) is the system I build at Arya Omnitalk for highway enforcement and incident monitoring. Each gantry has its own GPU box. It reads the camera streams, detects and tracks every vehicle, reads its number plate, measures its speed, checks it for violations, and stores the result as evidence. The control room gets checked events with photos and video, not raw footage.

Most enforcement systems only record violators. VIDS records every vehicle that passes, with class, plate, speed and evidence. That gives the road operator full traffic counts and a way to audit toll records, not only a list of fines.

The records are used as legal evidence, so the rule on this project is simple: being correct and staying up come before new features.

Hard problems, and how I solved them

A

No hardware encoder

Streams decode straight into GPU memory. The Orin Nano has no video encoder, so the live preview gets the original H.264 stream passed through instead of re-encoding it.

B

Latency that can't drift

Each camera keeps only its newest frame. If inference slows down, old frames are dropped, not queued, so the system stays close to real time instead of falling minutes behind.

C

Filter first, run models later

Cheap checks (ROI, lane, direction, size, track quality) throw away irrelevant vehicles before any expensive model runs. Models whose rules are switched off stay idle.

D

Plates you can trust

Contrast fix and sharpening before OCR, a penalty for blurry crops, fixes for O/0 and I/1 by position, and a plate is only final after 2 matching reads.

E

One slow model can't block a record

ANPR, helmet and seatbelt run in parallel worker pools on bounded queues. The finalizer joins their results per vehicle and has a timeout, so a slow model never holds up the record.

F

Seven models, one small GPU

All GPU work goes through one lock so TensorRT contexts never collide on an 8 GB Jetson. RT-DETR runs on a subset of frames and the pothole scan once an hour, which keeps everything inside the memory budget.

G

Three services, no shared code

The AI service, the dashboard and the ATMS sync only talk through the database, an SSE stream and an HTTP control API. Any one of them can be restarted or upgraded on site without touching the others.

H

Speed from one camera

Speed comes from the vehicle's track and a per-camera calibration (homography or a fitted row-to-metres curve). Each camera can use the method that suits its view.

Scaling up: from one gantry to 12 cameras on one GPU

Longer write-ups: the 12-camera scale-up and the dog that never raised an alert.

VIDS started on a Jetson Orin Nano at each gantry: 3 lane cameras and 1 overview camera. Some sites need many cameras in one place, so we moved those to a GPU server with an RTX 5060 Ti. How many cameras a box can take depends on the hardware, so I tested it: 12 cameras at 1080p with every detector switched on.

What broke

The first 12-camera run showed that about 90% of each camera's frame time was spent waiting for the GPU lock. Every overview camera loaded its own RT-DETR engine (about 12 engines) and ran it inside its own loop, so the cameras kept queuing behind each other.

The fix

  1. A shared pool of RT-DETR engines (one per gantry plus a spare), instead of one per camera.
  2. Cameras hand a request to the pool and pick up the result on a later frame, so they never wait.
  3. Each camera keeps only its newest request, and results older than 1 second are dropped, never applied.
  4. A hung or crashed engine is replaced automatically, and vehicle detection carries on while it's down.

The target is at least 7 fps per camera at an 8 fps cap on all 12 cameras. The Jetson setup stays as it was.

A field bug: the dog that never raised an alert

On site, a dog stood still in a lane and people walked on the road, and VIDS raised nothing. TMCS, running the same model on the same view, did alert. I reproduced it from the recorded frames and found two causes:

  1. The tracker never started a track for it. The tracker's default score fusion needs a fairly strong score to start a new track, and it drops a new track after one miss. A dog scoring around 0.4 never got an ID, and VIDS only looks at tracked objects. I shipped a config hotfix the same day, then ported the TMCS tracker, which keeps a weak new track alive for one miss.
  2. It was too small for the model. Squeezing the lane area into a 640 px input shrank the dog to about 14×20 px. On the full view the model read it as a "person" at 0.43; cropped, it was a dog at 0.85. Now wide areas are cut into tiles no wider than 960 px and the detections are merged.

Every step that drops a detection is now counted in a per-minute log line, so the next silent miss is visible in the logs instead of only showing up in the field.
